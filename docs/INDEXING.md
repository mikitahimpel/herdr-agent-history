# Incremental indexing and preview behavior (#3, #8, preview portion of #5)

The index assigns each discovered path a database-wide integer identity. Native inode and device identity, nanosecond change time, SHA-256 hashes of the first and last 4 KiB, the real parser session metadata, and bounded open-turn state are stored together with committed progress. Hash inputs are not stored. An append reads new transcript bytes plus at most 8 KiB of previous boundary content for verification. `bytes_read` reports the transcript stream, excluding these bounded verification reads.

Only complete newline-terminated records advance the offset. Incomplete UTF-8 or JSON tails are retried. Malformed JSON and records larger than 4 MiB are counted and skipped once complete; subsequent valid records continue. Unknown supported-format records contribute metadata if available but no searchable event. Readers retain at most one bounded record; derived chunks for a file are collected until its atomic transaction, so total batch memory can still grow with that file's extracted text.

Size/mtime/ctime changes and inode replacement detect same-size rewrites and truncation. Growth is accepted as append only if device/inode and the previous boundary hashes still match. This does not detect every possible interior rewrite followed by regrowth: changes outside both sampled boundaries can evade append classification. Proving arbitrary historical immutability would require rereading all committed content. A source mutation observed during parsing or before commit aborts without advancing progress. Native files are not locked, so filesystem mutation immediately after the final validation remains possible; preview validates again.

Chunks, source removals, FTS updates, parser metadata, and open-turn state commit atomically. A writer obtains a SQLite immediate transaction and compares its previously observed progress before applying any changes. Concurrent attempts with obsolete progress or colliding new file identities fail recoverably instead of overwriting newer state. Chunk identity includes native session, source identity, generation, and ordinal, so two source files with the same native session cannot overwrite each other's chunks.

Missing originals retain their existing searchable history and metadata; preview reports an error. Renames are treated as a missing old path plus a new path, so retained old search results can coexist with the newly discovered source. The current API performs a synchronous activation scan, reports counts and up to 32 file/discovery failures, and continues unrelated files. A bounded progress callback reports global and per-agent file counts, bytes read, records parsed, and derived chunks during the scan. The overlay shows this work with a live elapsed timer, including while preparing the index. Search starts after the scan. There is no daemon or cancellation API; Ctrl-C during startup exits the process and uncommitted per-file work is retried on the next launch. Separate SQLite readers can use previously committed results through WAL; responsive UI activation still requires host scheduling.

## Git provenance (#4)

Git facts are persisted with the origin that produced them, and the two origins are never merged into one claim.

`Observed` facts come from read-only `git` invocations against the session cwd while indexing: repository root, worktree, branch, HEAD commit, and the configured `origin` remote. Observations are cached per cwd within one scan. They describe the repository at index time and are not proof of historical branch state.

`Recorded` facts come from the native transcript itself. Codex writes a `git` block into its rollout `session_meta` with `commit_hash`, `branch`, and `repository_url`; Claude Code writes `cwd` and `gitBranch` on each conversational line and `prRepository` when a pull request is in play. A missing block, a block that is not an object, non-string fields, an empty branch, and the literal `HEAD` of a detached checkout all yield no recorded provenance. Recorded facts are historical claims about the session, not statements about the repository today.

Recorded provenance never supplies a `repository_root` or `worktree`. A remote URL says which repository a session belonged to; it does not say where that repository or its worktree lived on disk. `repository` holds an `owner/name` label derived from the recorded URL, and the URL itself is persisted unchanged in `repository_url`. Recovery that needs a local path must therefore still refuse a recorded-only session, while recovery that only needs repository and commit identity can proceed.

Precedence within one indexing pass: a successful live observation wins; otherwise a previously stored observation is kept, because it knows where the worktree lived; otherwise the transcript's own record applies. Recorded values are taken first-wins per field, so a branch switch late in a session does not rewrite the context the session started in, and they are carried across appends in the checkpoint. Checkpoints written before provenance was labelled are read as observations, since only a live `git` invocation could ever have filled those fields.

The origin is available on `SearchResult::git_origin`, from `SqliteStore::session_record`, and from `preview::session_record_for_source`. `Session`, `SqliteStore::session`, and `preview::session_for_source` are unchanged and keep returning the flat fields without the origin.

Backfilling recorded provenance requires reparsing existing sources, so schema 4 also raises the checkpoint format marker. Each available source is reindexed once on the next pass; the native JSONL is only read.

## Free space reclamation (#2)

A migration or rebuild that mass-deletes rows leaves free pages behind, and SQLite reuses them rather than returning them to the filesystem. Both mechanisms are used deliberately:

- New databases are created with `PRAGMA auto_vacuum=INCREMENTAL`, which is only possible while no table exists. Routine rebuild churn is then released by `PRAGMA incremental_vacuum` at the end of each full indexing pass, without rewriting the file.
- An existing database is switched to incremental auto-vacuum by `VACUUM`, which is the only way to change the mode after the fact. `VACUUM` cannot run inside a transaction and needs scratch space about the size of the database, so it runs after the migration transaction commits, only when a schema upgrade actually occurred, only when free pages exceed a quarter of the file and at least 64 pages, and only when the filesystem reports room. A skipped or failed reclamation leaves a correct index that is merely larger than necessary.

Reclamation never touches native JSONL, runs outside the batch transaction, and does not change committed offsets, source generations, or chunk identities, so the transactional-offset guarantees are unaffected and rebuilds stay idempotent.

Preview requires the store and a source reference. It validates indexed identity/generation and current source metadata, then normalizes complete original records through the appropriate native adapter into role-separated text. Controls are replaced before terminal rendering. Context is capped at 1 MiB on each side and the entire read window at 8 MiB; records exceeding the parser limit or partial window edges are omitted. Missing/replaced or unindexed changed sources fail explicitly. Repository/branch context remains available on the associated search result/session.

Schema 4 adds the session provenance columns `git_origin` and `repository_url`. Upgrading from schema 3 or 2 backfills `git_origin` as observed wherever a repository root was already stored, because nothing but a live observation could have produced one. Schema 3 automatically upgrades schema 2: it removes mixed-speaker/tool search chunks and retains source identities, checkpoints, and captured session context. A checkpoint format marker forces each available source to be reindexed as user/assistant chunks; a verified format-only rebuild preserves saved Git context even if the cwd has disappeared. Old tool text cannot remain searchable during the upgrade. Missing native sources cannot supply replacement searchable text. Close older running clients before launching the new build. The upgrade reclaims the free pages the rebuild leaves behind, so the file shrinks rather than staying at its previous size.

Schema 4 still rejects the unreleased schema 1 index with an explicit rebuild message. A schema 1 database cannot safely retain its colliding source/chunk identities. Close all clients before removing only the disposable index database and its SQLite sidecars, then rebuild from native histories. Never remove native agent session directories.

Validation uses isolated synthetic files and temporary Git repositories: both native adapters through discovery/index/query/normalized preview; metadata-only first record and appended continuation across database reopen; whole-file chunk equivalence; partial Unicode/newline tails; oversized/malformed records; same-size rewrite, truncate/regrow, inode replacement, rename/deletion; mutation during parsing; competing writers; retained Git context; source-isolated FTS removal; recorded provenance in both adapters, including absent, malformed, partial, non-Git, and detached-HEAD cases; observed provenance outranking a recorded claim and surviving its worktree's deletion; and post-migration compaction of a synthetic legacy database. No private histories or native agent processes are used. These tests do not substitute for native-agent, Herdr, installation, performance, or full release acceptance evidence.
